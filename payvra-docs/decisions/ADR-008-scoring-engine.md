# ADR-008 — Explainable weighted rules over a trained model

**Status:** Accepted
**Date:** 2026-08-23

## Context

The worklist ranking is PAYVRA's most visible piece of intelligence — it is the first thing a
merchant sees and the first thing a judge evaluates. FR-4.3 requires every ranked row to carry a
plain-English reason for its position.

We have no historical payment data to train on. Seed data is synthetic.

## Decision

**MVP: explainable weighted rules.** Feature weights are explicit constants in `scoring/model.py`.
The reason string is generated by templating the top three contributing features.

`priority = p_collectable * amount_at_risk * urgency_multiplier`

Where `p_collectable` is a weighted sum of normalised features passed through a logistic function.

**Roadmap: LightGBM** once real payment outcomes exist. CPU-trained, seconds on 10k rows.

## Rationale

**Why not train a model now:** training on synthetic data we generated ourselves produces a model
that has learned our own seed-data assumptions. It would look sophisticated and mean nothing. A
judge who asks "what did you train on?" would expose it immediately.

**Why explainability is the actual requirement:** a finance lead will not act on a ranking she
cannot justify to her CFO. "₹4.2L, 68 days, this customer has paid late twice before but always
paid" is more useful than a 0.74 with no provenance. Weighted rules give that for free; a
gradient-boosted model needs SHAP values to approximate it.

**Why LightGBM later, not a neural net:** tabular data with a few dozen features. Gradient boosting
beats deep learning here, trains on CPU in seconds, and keeps the no-GPU property from ADR-003.

## Feature weights (initial, tune on seed data)

| Feature | Weight | Direction |
|---|---|---|
| `counterparty_avg_days_to_pay` within terms | +0.30 | reliable payers are collectable |
| `broken_promise_count` | −0.25 | strongest negative signal |
| `engagement_rate` (opens, clicks, replies) | +0.20 | engagement predicts payment |
| `has_dispute` | −0.40 | disputes are not a collections problem |
| `days_past_due` | −0.15 | decays with age |
| `lifetime_revenue` (relationship value) | +0.10 | worth more effort |
| `touch_count` | −0.10 | diminishing returns |

`urgency_multiplier`: `1.0` base, `1.3` if `crosses_msme_45`, `1.5` if approaching a limitation
period, `0.5` if a promise is open and not yet due.

**These weights are a starting point and an assumption, not a finding.** Tune against seed data
until the ranking is intuitively defensible, and say so honestly if a judge asks.

## Alternatives considered

**Sort by days past due.** What every existing aging report does. Rejected: it is exactly the
behaviour we are claiming to improve on. Oldest is rarely most collectable.

**Sort by amount.** Rejected: ignores collectability entirely. Chasing an unrecoverable ₹10L is
worse than collecting three recoverable ₹1L invoices.

**LLM ranks the worklist.** Rejected firmly. Non-deterministic ordering, unexplainable, slow, and
burns rate limit on something arithmetic solves. Ranking must never depend on an LLM call —
see `architecture/components.md`.

**Train LightGBM on synthetic data.** Rejected as intellectually dishonest, per above.

## Consequences

**Good:** Fully explainable; deterministic and testable; no training data needed; reason strings
are always consistent with the score; zero LLM cost in the ranking path

**Bad:** Weights are hand-tuned assumptions; will underperform a trained model once real data exists;
requires manual retuning as behaviour changes

**Migration path:** keep `scoring/features.py` separate from `scoring/model.py`. Feature extraction
is unchanged when the model swaps; only the combination function changes. Log every score with its
feature vector from day one so there is a training set when real outcomes arrive.
